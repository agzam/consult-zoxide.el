#+begin_quote
Jump to any directory [[https://github.com/ajeetdsouza/zoxide][zoxide]] remembers, from a Consult prompt - annotated, narrowable, and prunable.
#+end_quote

* What

[[https://github.com/ajeetdsouza/zoxide][zoxide]] is a smarter ~cd~: it remembers the directories you work in and ranks them by frecency. This surfaces that database in Emacs as a [[https://github.com/minad/consult][Consult]] prompt.

: M-x consult-zoxide

Entries stay in zoxide's frecency order. Each row carries its score and, for git checkouts, the branch that is currently out.

* Why not just a completing-read over ~zoxide query --list~

Because the interesting part is everything around the list.

A database that has been accumulating for a couple of years is mostly rot: deleted worktrees, build directories that no longer exist, ~/tmp~ scratch dirs from six months ago. There was no way to see any of that, let alone remove it. And a flat list of paths tells you nothing about which of five identically-shaped worktree directories you are about to open.

* Prior art

[[https://git.sr.ht/~vonfry/zoxide.el][zoxide.el]] by Ruoyu Feng is the other Emacs package for zoxide, and it came first. It wraps the binary in a ~completing-read~ with no dependencies at all: ~zoxide-find-file~, ~zoxide-cd~, ~zoxide-travel~, plus ~zoxide-add~ and ~zoxide-remove~ taking one path each. Prefer it if you want the plain thing, or if you do not use Consult.

This package goes the other way and builds on Consult: annotations on every row, narrowing, dead-entry pruning in one batched call, an Embark keymap and a ~consult-dir~ source. Everything in the sections below is the difference between the two.

[[https://github.com/karthink/consult-dir][consult-dir]] solves an adjacent problem - switching the directory a prompt runs in - and reads recentf, project and bookmark directories rather than zoxide. The two compose - see the consult-dir section below.

* Annotations

Every row shows its frecency score, right-aligned.

Git checkout roots also show their branch. The branch is read directly out of ~HEAD~ - no git process is spawned - and only for the rows the completion UI actually has on screen, so the cost does not scale with the size of the database. Reading ~HEAD~ costs about a tenth of a millisecond; running ~git symbolic-ref~ costs twelve, which at fifteen visible rows would be a fifth of a second on every keystroke.

The branch is suppressed when it merely repeats the directory name. Under a worktree-per-ticket layout the directory is named after its branch, so echoing it back would put a column of noise on every worktree row.

Directories that no longer exist are struck through.

* Narrowing

| key | keeps                                    |
|-----+------------------------------------------|
| ~g~   | git checkout roots                       |
| ~w~   | worktrees                                |
| ~d~   | entries whose directory no longer exists |

Worktrees are distinguished from submodules properly: both keep ~.git~ as a file rather than a directory, and only reading it tells them apart. A submodule names its gitdir relatively, so it only resolves against the directory holding it.

* Pruning

Dead entries are left out of the list by default, being nothing but noise while navigating. A prefix argument brings them in:

: C-u M-x consult-zoxide

From there, narrow with ~d~, then ~embark-act-all~ and the removal key. Removal is registered as an Embark multi-target action, so the whole set goes to zoxide in one batched call rather than one process per entry - about thirty times faster for a realistic prune.

** The guard

~consult-zoxide-remove~ asks before a bulk removal that includes a directory which still exists.

This is not paranoia. ~embark-act-all~ with no selection acts on every candidate currently matching, and with ~embark-confirm-act-all~ set to nil a forgotten narrow would empty the entire database on one keystroke. There is no undo: re-adding a path restores neither its score nor its recorded access time.

One entry at a time is never questioned, dead or alive, and neither is a batch whose every path is already gone - the prune above. Anything else asks, naming the size of the batch and how many of it are live, which is what a forgotten narrow gives away. Declining touches nothing.

The question is there because a deliberate selection cannot be told from a mis-narrow by the time the action runs. ~embark-select~ keeps the selection in a variable local to the minibuffer, and under ~embark-quit-after-action~ the action runs from ~post-command-hook~ with that minibuffer already gone, so the action sees a list of paths and nothing else. The count is all the signal there is.

The check re-stats at removal time rather than trusting the candidate's ~dead~ tag, so it holds however the function was reached.

* Embark

Opt in with one line:

#+begin_src emacs-lisp
(with-eval-after-load 'embark
  (consult-zoxide-embark-register))
#+end_src

~consult-zoxide-embark-register~ is autoloaded, so that needs no ~require~. Nothing registers on its own: installing the package leaves Embark exactly as it was. Embark is not a dependency either, so without it nothing here is affected.

It gives the ~consult-zoxide-dir~ category a keymap inheriting from ~embark-file-map~, so every file action applies, and puts removal on ~\~ - the key Embark already uses for dropping a recentf entry.

~d~ is rebound to ~delete-directory~, the inherited ~delete-file~ having nothing to act on where every candidate is a directory. Both it and ~D~ delete off disk, behind the confirmation prompt Embark's own ~embark-pre-action-hooks~ already puts in front of them.

~embark-quit-after-action~ is left alone. Whether the prompt survives a removal is your setting to make, and either answer works: the prompt either closes or comes back without the rows just removed.

The refresh takes a detour worth knowing about. Embark restarts a prompt with ~embark--restart~ on ~embark-post-action-hooks~, and that function returns early unless a minibuffer is current. For a multi-target action ~embark--act~ runs those hooks inside ~with-selected-window~ on the *target* window, so the test fails and the refresh silently never happens. Every action Embark itself restarts is single-target, which is why the combination goes unnoticed. ~consult-zoxide-embark--restart~ makes the minibuffer current first.

* consult-dir

Same arrangement for [[https://github.com/karthink/consult-dir][consult-dir]]:

#+begin_src emacs-lisp
(with-eval-after-load 'consult-dir
  (consult-zoxide-consult-dir-register))
#+end_src

That appends a "Zoxide" source to ~consult-dir-sources~, reachable under the ~z~ narrowing key. consult-dir is not a dependency.

The source is ~consult-zoxide-directory-source~, should you want to reorder or replace it.

Its rows carry the Embark actions above, so ~\~ forgets an entry from the ~consult-dir~ prompt as well - the same key as in ~consult-zoxide~ itself.

That takes a small trick, worth knowing if you write your own source. ~consult--multi~ stamps each candidate with a ~multi-category~ datum built from its source's ~:category~, and Embark reads that datum to choose a keymap. Declaring ~:category consult-zoxide-dir~ would therefore be the obvious thing, and it breaks consult-dir: ~consult-dir--pick~ turns the match back into a directory with a ~pcase~ over the source's category that handles ~file~ and ~bookmark~ only, so anything else opens nothing. But consult leaves a datum a candidate already carries alone, so the source declares ~:category file~ for consult-dir while its items carry ~(consult-zoxide-dir . PATH)~ for Embark, and both get the answer they need.

* Installation

Requires the ~zoxide~ binary on ~PATH~.

#+begin_src emacs-lisp
(use-package consult-zoxide
  :ensure (consult-zoxide :host github :repo "agzam/consult-zoxide.el")
  :commands (consult-zoxide consult-zoxide-read)
  :config
  (consult-zoxide-track-mode 1))

;; optional, see below
(with-eval-after-load 'embark
  (consult-zoxide-embark-register))

(with-eval-after-load 'consult-dir
  (consult-zoxide-consult-dir-register))
#+end_src

* Tracking

~consult-zoxide-track-mode~ records directories visited in Dired, so zoxide learns from Emacs and not only from the shell.

Only Dired is hooked. ~consult-zoxide-track~ works in file buffers too, and you can put it on ~find-file-hook~ yourself, but recording the directory of every file you open fills the database faster than it is worth - which is how you end up needing the pruning above.

* API

| function                   | does                                                            |
|----------------------------+-----------------------------------------------------------------|
| ~consult-zoxide~             | the command: prompt, then visit                                 |
| ~consult-zoxide-read~        | prompt and return the directory, for callers that want the path |
| ~consult-zoxide-directories~ | the bare path list, for feeding another completion source       |
| ~consult-zoxide-remove~      | drop entries, guarded as above                                  |
| ~consult-zoxide-track~       | record the current buffer's directory                           |
| ~consult-zoxide-track-mode~  | do that automatically for Dired                                 |

~consult-zoxide-directories~ takes no required arguments, which is what makes it usable as a source's ~:items~ - see consult-dir below.

~consult-zoxide-read~ takes an optional query, which is handed to zoxide's own matcher and skips the prompt entirely when it singles out one directory - the shell ~z~ contract. That makes an Eshell ~z~ a one-liner:

#+begin_src emacs-lisp
(defun eshell/z (&optional query)
  (eshell/cd (consult-zoxide-read query)))
#+end_src
